1. Real-World Justification for Each Algorithm
In the AuctionHub system, each module deals with a different type of bid data and performance requirement, so using a single sorting algorithm everywhere would not be efficient. Here is why each algorithm fits its assigned module:
•	Insertion Sort (Module A - Live Auction Monitor): Incoming live bids arrive in nearly-sorted order because each new bid is usually slightly higher than the previous one. Insertion Sort works in O(n) time on nearly-sorted arrays since out-of-order bids only need to shift back by one or two positions, and it avoids the recursion overhead of more complex sorts.
•	Selection Sort (Module B - Top-K Bid Finder): For the Top 3 Bidders widget, we only care about extracting the largest values from a small set of bids. Selection Sort naturally finds the maximum element in each pass and moves it to the front in-place without extra memory, and it minimizes the total number of struct swaps.
•	Interchange Sort (Module C - Price Anomaly Validator): This QA check runs on very small batches of at most 50 records before they enter the database. For n <= 50, an O(n^2) algorithm finishes in just a few microseconds, so Interchange Sort is completely acceptable and its straightforward nested loop makes the validation logic easy to read and verify.
•	Bubble Sort with Early Stop (Module D - Stabilization Detector): To check if a 10-minute price stream has stabilized, we only need to know whether any adjacent bids are out of order. With the swapped flag, Bubble Sort checks the whole array in a single pass and stops immediately in O(n) time if no swaps occur, while still sorting the window if changes are detected.
•	Quick Sort (Module E - Full Historical Sorter): End-of-day reports require sorting hundreds of thousands or millions of historical bids, where O(n^2) algorithms are far too slow. Quick Sort achieves O(n log n) average-case performance, runs in-place without allocating a second large array, and takes good advantage of CPU cache locality.
2. Quick Sort Benchmark on 100,000 Records
To test Module E at scale, I generated 100,000 random Bid records using std::mt19937 and measured the runtime of my Quick Sort (with median-of-three pivot selection) using std::chrono::high_resolution_clock. On my machine, sorting all 100,000 records took approximately  22.301 ms and passed the ascending order check.
3. Debugging Experience: One Bug I Encountered
While testing edge cases, I ran into a bug in quickSortWrapper when passing an empty vector (v.size() == 0), which caused a segmentation fault. After checking the index values, I realized that v.size() returns an unsigned size_t in C++, so writing v.size() - 1 on an empty vector underflowed to a huge positive integer instead of -1. I fixed this by adding a guard condition (if (v.size() <= 1) return;) at the start of quickSortWrapper before calling quickSort.

5. Worst-Case Complexity of Quick Sort with Median-of-Three
Yes, the theoretical worst-case time complexity of Quick Sort with median-of-three pivot selection is still O(n^2). Although picking the median of the first, middle, and last elements solves the O(n^2) problem on already-sorted and reverse-sorted arrays (because the middle element splits those inputs evenly), it is still a deterministic rule that only looks at three fixed indices. In theory, an input array can be crafted so that at every recursive call, the elements at lo, mid, and hi happen to be the three smallest (or three largest) elements in that subarray. That would still produce badly unbalanced partitions at every step, leading to O(n^2) comparisons.
